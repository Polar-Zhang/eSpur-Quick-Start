# eSpur 组网排障

现行拓扑见 [全网台账](topology.md) 和 [组网入口](../SKILL.md)。本页替代旧新加坡双端口、自动注册和 51821 UDP 中转的排障步骤；旧脚本和看门狗不得重新运行或安装。

先区分要排查的是北京 eSpur `espur-wg0`（51822/udp，10.66.66.0/24）、北京用户自有 `wg0`（51820/udp，10.10.10.0/24），还是某台 peer 的本地接口。两套网络共用主机，不能笼统重启 `wg0`。

## 分层确认

1. **主机和接口**：查看 `ip -br address`、`ip -4 route show` 及目标接口的 `systemctl status`；核对站点、接口名、地址、MTU 和当前角色。
2. **WG 层**：对已确认接口分别查看 `sudo wg show <接口> endpoints`、`latest-handshakes` 和 `transfer`。握手有时只证明 peer 与 hub 近期交换过报文，不证明其他节点或上报正常。
3. **路由层**：针对确定站点的目标执行 `ip route get <目标地址>`，核对源地址和出口。lab 与 Studio 的 PDU 都可能是 `192.168.0.163`，必须结合站点核实，不能由地址单独判断。
4. **转发层**：仅在有权限的目标节点检查 peer 的 AllowedIPs、内核路由、IP 转发和现有 NAT 规则。修改或重启前，先保留配置、评估对两个 WG 的影响和恢复通道。
5. **平台上报**：单独检查设备到 `neowatt.cn` 的 HTTPS 路径、服务状态和平台采样；lab 走北京 TCP 中转，Studio 侧按台账直连。不要把 WG 丢包自动归因于 HTTPS 或反过来。

ICMP 成功不能证明 UDP 51822 可达；UDP 超时也可能是出口、路径、防火墙、服务或密钥问题，不能只凭另一个端口上的 STUN/NTP 或未监听 UDP 端口断定原因。应在已授权范围内结合两端配置、监听、握手和日志判断。

不要为排障自动更改 Endpoint、禁用 SELinux、覆盖配置、重跑旧入网脚本，或对 PDU 做并发扫描。需要 PDU 探测时先确认站点、速率和影响；只读请求也会给设备造成负载。
